# The Bonnet Protocol, as implemented over HTTP

See also:

- [spec.md](spec.md) — the full protocol specification
- [OPERATOR_GUIDE.md](OPERATOR_GUIDE.md) — deployment and operations

## Underlying protocol

The protocol runs over HTTPS. Requests and responses are signed using
RFC 9421 HTTP Message Signatures with Ed25519. The signature tag is
`bonnet-firehose-1`. Content type is
`application/vnd.bonnet.command`. Content digest is sha-256.

The protocol is stateless. No session is kept by the server on behalf of
the client. Each request carries its own signature and nonce.

## Discovery

GET /.well-known/bonnet

Transfer the server's signed discovery document back. It contains the
origin string, public key, anonymous key pair, capabilities, and known
origins. The response is signed by the server's own key. The client
TOFU-pins the key after first verified contact.

## Commands

POST /command

Send a binary body starting with a one-byte opcode. Get back a binary
response starting with a status byte (0 = success, 1 = error). Errors
include a u16 code and a UTF-8 message.

## Records

A record is a signed, chain-linked entry in an origin's firehose. It
contains a kind, the actor's identity and signature, the origin's
signature, a sequence number, the previous event's hash, metadata, and
an optional body reference. Records are append-only and immutable once
accepted.

## Federation

One server syncs from another by fetching heads and record ranges over
the command protocol. Records are fetched in bounded batches, verified
against the chain and signatures, and accepted. The syncing server
creates a signed witness for each accepted record naming its upstream
source. Failed peers accumulate exponential backoff with jitter.

## Status codes

    0x0000  internal error
    0x0001  user not found
    0x0002  head not found
    0x0003  object not found
    0x0004  not permitted
    0x0005  unhandled opcode
    0x0006  validation error
    0x0008  body purged
    0x0009  conflicting state
