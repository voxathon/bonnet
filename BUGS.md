# Bugs

Findings from a code review of `src/bonnet`'s highest cognitive-complexity functions (via `complexipy`). Review-only — no fixes applied yet.

| # | Severity | File:Line | Category | Summary | Failure Scenario |
|---|----------|-----------|----------|---------|-------------------|
| 1 | High | [src/bonnet/core/acl.py:42](src/bonnet/core/acl.py#L42) | security | `PrincipalMatcher.matches()` checks match fields in priority order and returns on the first non-`None` one, so a matcher with both `role` and `origin` set silently ignores the `origin` constraint. | An ACL rule with `match.role="moderator"` and `match.origin="trusted.example"` grants access to moderators from **any** origin, since `matches()` returns on the role check before reaching the origin check. Nothing rejects setting both fields. |
| 2 | High | [src/bonnet/core/board_projection.py:985](src/bonnet/core/board_projection.py#L985) | correctness | `query_articles()` sets `has_visibility_filter=True` for any `field_id==0x06` filter, but only appends a WHERE clause for op `0x01`/`0x02` or `value=="purged"` — an unsupported operator disables the default `visibility=active` fallback entirely. | A raw `OP_ARTICLE_QUERY` request with filter `(0x06, 0x03, "active")` sets the flag but adds no clause, skipping the default fallback, so cancelled/superseded articles leak into results. |
| 3 | Medium | [src/bonnet/net/firehose_http_server.py:323](src/bonnet/net/firehose_http_server.py#L323) | correctness | Authenticated requests are rate-limited against **both** the identity bucket and the address bucket, while anonymous requests only check the address bucket — contradicts the documented identity-or-address design. | A registered user behind a shared NAT/proxy gets 429'd because the shared address bucket is drained by unrelated traffic, even though their own identity bucket has budget — inverting the intended trust model. |
| 4 | Medium | [src/bonnet/net/firehose_commands.py:516](src/bonnet/net/firehose_commands.py#L516) | correctness | Article/event bodies are staged/written to disk before `append_record` verifies the actor signature; if verification fails, the exception is caught generically and the already-written body file is never cleaned up. | Repeated `OP_PUBLISH_RECORD` requests with a valid body hash/size but invalid `actor_sig` accumulate orphaned body files on disk with no cap — a slow disk-fill DoS vector. |
| 5 | Medium | [src/bonnet/net/firehose_commands.py:430](src/bonnet/net/firehose_commands.py#L430) | correctness | The per-kind control-event validation chain has no branch for `KIND_ARTICLE_PIN`, unlike its symmetric counterpart `KIND_ARTICLE_UNPIN`, which rejects a redundant unpin. | Publishing `KIND_ARTICLE_PIN` against an already-pinned article is silently accepted and appended as a duplicate event, unlike every other control kind (CANCEL, RESTORE, PURGE, THREAD_CLOSE, THREAD_REOPEN) which reject their own no-op transitions. |
| 6 | Medium (plausible) | [src/bonnet/net/firehose_sync.py:131](src/bonnet/net/firehose_sync.py#L131) | security | `is_safe_dial_target` (Gate C SSRF protection) runs once in `HttpSyncClient.__init__` and is never rechecked; the same client is reused for the lifetime of a long-running periodic sync loop. | An attacker controlling DNS for a configured peer hostname passes validation with a public IP, then repoints the hostname to an internal address for later sync cycles — no re-validation ever occurs. |
| 7 | Low | [src/bonnet/core/config.py:236](src/bonnet/core/config.py#L236) | correctness | The peer-origin duplicate check compares raw, unnormalized `peer.origin` strings, while the server's own `self.origin` is lowercased via `_normalize_origin` at construction. | Config entries `origin="Example.com"` and `origin="example.com"` are treated as distinct peers, defeating the duplicate-peer guard. |
| 8 | Low | [src/bonnet/app/console.py:900](src/bonnet/app/console.py#L900) | correctness | `--limit=` is parsed with a bare `int()` that only catches non-numeric input; an out-of-range value passes parsing and later fails at `struct.pack(">H", limit)` with an unhandled `struct.error`. | `query-articles <board> --limit=-1` (or `--limit=99999`) crashes with a raw `struct.error: ushort format requires 0 <= number <= 65535` instead of the intended "Invalid limit" message. |

## Notes

Two SSRF-adjacent claims from the initial finder pass (IPv4-mapped IPv6 literals and `0.0.0.0/8` bypassing `is_safe_dial_target`'s private-range checks) were tested directly against Python's `ipaddress` module and found to already be correctly blocked (`is_private` catches both cases) — dropped as false positives, not listed above.
